# 写作语气

同样的内容，语气不同，读者的完成率能差一倍。

## 一、原则：把读者当成"三分钟后的自己"

写文档时最容易犯的错，是**默认读者已经知道你知道的一切**。

| 预设读者知道 | 实际情况 |
| --- | --- |
| 这个术语的含义 | 他是搜关键词进来的，只懂表层 |
| 为什么要先做 A 再做 B | 他只想照做，不想理解原理 |
| 报错是正常的 | 他会以为项目坏了，直接关掉页面 |

**判断方法**：把你写的段落隔一天再读一遍，如果有一句话需要调用"上下文记忆"才能懂，
那它就该补一句解释。

## 二、语气：中性、直接、可验证

| 场景 | 不推荐 | 推荐 |
| --- | --- | --- |
| 介绍功能 | 强大的性能优化能力 | 构建耗时从 30 秒降到 3 秒 |
| 说明限制 | 目前还不支持 | 当前不支持 X，替代方案是 Y |
| 提示风险 | 注意可能有坑 | 该操作会覆盖原文件，执行前请备份 |
| 引导操作 | 是不是很神奇呢？ | 打开 `http://localhost:5173` 查看效果 |

核心是**去掉情绪词，留下事实**：

- ❌ 极致、强大、优雅、丝滑、开箱即用（滥用后无意义）
- ✅ 数字、版本号、平台名、耗时、体积、限制条件

## 三、结构：先说结论，再说原因

中文文档习惯"起承转合"，但技术文档读者是**带着问题来扫读的**，不是来读散文的。

```md
❌ 铺垫式写法：
由于在构建过程中，VitePress 需要遍历所有 Markdown 文件...
（三百字后）...因此你需要设置 base。

✅ 结论先行写法：
部署到子路径时必须设置 base，否则样式会丢失。
原因是构建产物使用绝对路径引用资源。
```

## 四、命令类内容：动词开头，一步一句

```md
❌ 你可以在项目根目录里通过执行下面这条命令来安装所有的依赖：
✅ 安装依赖：
```

祈使句在中文技术文档里是完全得体的，不必加"请"字堆砌礼貌。

## 五、处理"不知道"和"还不支持"

诚实说明限制，比含糊其辞更能建立信任。

| 情况 | 写法 |
| --- | --- |
| 确定不支持 | 当前不支持 X。 |
| 计划支持 | 计划在 v2.0 支持 X，见 [议题 #123](https://github.com/bluetn514/vitepress-zh-starter/issues)。 |
| 尚未验证 | 未在 Windows 上验证，欢迎[反馈](https://github.com/bluetn514/vitepress-zh-starter/issues)。 |
| 已废弃 | ⚠️ 该参数自 v1.5 起废弃，请改用 Y。 |

**不要**写"暂时不支持"却不说清是几天还是几年。

## 六、避免三种常见毛病

### 1. 同义堆砌

```md
❌ 一个强大、灵活、易用、高效的现代化解决方案
✅ 一个把 CSV 转成 JSON 的命令行工具
```

### 2. 悬空指代

```md
❌ 这个配置很关键，它会影响之前的那些设置。
✅ base 配置很关键，它决定所有静态资源的引用路径。
```

### 3. 长定语

```md
❌ 一个可以在不修改现有配置文件的前提下支持多环境的方案
✅ 该方案支持多环境，且不需要修改现有配置文件
```

中文读者对超过 15 字的定语会"读断气"，拆成短句。

## 七、面向不同读者的分层

一套文档要给三类人看，层次要分开：

| 读者 | 想看 | 放在哪 |
| --- | --- | --- |
| 初次接触 | 这是什么、值不值得用 | 首页 + 指南/简介 |
| 准备使用 | 怎么装、怎么跑起来 | 指南/安装、快速上手 |
| 已经用上 | 某个参数是什么行为 | 参考/API、常见问题 |

**常见错误**：把"这是什么"写成三百字原理介绍放在安装页开头，
挡住了只想复制命令的读者。

## 八、语气自检

- [ ] 没有"极致/强大/优雅/丝滑"等无信息量形容词
- [ ] 每个功能描述都能追溯到可验证的事实或数字
- [ ] 结论在段落开头，原因在后
- [ ] 命令类内容用祈使句，一步一句
- [ ] 限制和已知问题写清楚了，且没说"暂时"
- [ ] 没有超过 15 字的定语
- [ ] 三类读者各自能在三层点击内找到需要的内容
